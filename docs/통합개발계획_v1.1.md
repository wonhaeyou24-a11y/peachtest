## A. 앱 아키텍처 정밀 지도

### A-1. 파일 구조
- **완전 단일 파일 PWA**: `index.html` 한 개에 CSS·HTML·JS 전부. 빌드 시스템 없음.
- 외부 라이브러리는 CDN + Service Worker 캐시: `docx@8.0.4`, `xlsx@0.18.5`, `leaflet`, `jszip`. 전부 **지연 로딩**(`loadScriptOnce`) — 버튼 누를 때만.
- `service-worker.js` — 캐시 분리, standalone PWA.
- `.agents/rules/peachshot_regression_protection.md` — **회귀 보호 규칙**(핵심 함수 임의수정 금지, ZERO DATA LOSS, REG-01~30 검증).

### A-2. 데이터 모델 (로컬 = Source of Truth, IndexedDB)
```
projects[]        — { id, name, organizationId, damageMaster, revision, cloudSyncedAt, ... }
  └ (sites는 별도 최상위 배열, projectId로 연결)
sites[]  (=facilities) — { id, projectId, name, facilityType, facilityForm,
                           drawings[], markers[], existingDamages[],
                           nextExistingDamageNum, revision, schemaVersion }
    ├ drawings[]        — { id, name, type, imageSrc(dataURL/PDF), order }
    ├ markers[] (=지점) — { id(랜덤 s+ts+rand), num, xPct,yPct, drawingId,
    │                        lat,lng, gps, photos[], revision }
    │   └ photos[]      — { id, src(dataURL), cloudRef, note, damages[] }
    │       └ damages[] (InspectionDamage)
    │            — { id, damageOrigin:'NEW'|'EXISTING', existingDamageId,
    │                 component, damageType, damageDetail,
    │                 measurement(자유텍스트), measurementItems[]{type,label,value,unit},
    │                 cause, failureFactor, evaluation, repairMethod,
    │                 reinforcementMethod, urgency, investigatorComment,
    │                 standardReference, changeStatus }
    └ existingDamages[] (ExistingDamage)
         — { id:'EX-DMG-001', damageName, drawingPosition(위치), surveyYear,
              component(구성요소), measurement(자유텍스트), cause, repairMethod,
              status, notes, photos[], isDeleted, createdAt, updatedAt }
```
- **저장 경로**: `saveState()` → `performSaveState()` → `storageSet(STORAGE_KEY, snapshot)` (IndexedDB kv). 사진 Blob은 `photoBlobs` 전용 스토어. 지점은 `inspectionPoints` durable 스토어에도 이중 저장(`idbPutInspectionPoint`).
- **스냅샷**: `maybeTakeSnapshot()` — 주기적 자동 백업 N개 순환.
- **스키마 마이그레이션**: `runMigrations()` + `MIGRATIONS[]` (필드 없으면 v1로 간주, 기존 필드 미변경).

### A-3. 클라우드 동기화 (Supabase) — **현재 실제 동작**
테이블: `ps_projects`, `ps_facilities`, `ps_inspection_points`, `ps-photos`(storage), `ps_photo_index`, 조직/초대 RPC.

| 경로 | 트리거 | 보내는 것 |
|---|---|---|
| **자동 백그라운드** (`saveState`→`queueCloudSync`→`enqueueEntitySync`→`syncSingleEntity`) | 저장할 때마다 | **`ps_projects` 행 1개뿐** (payload `{id}`, `data:proj`). proj에는 sites/markers/사진 **미포함** |
| **수동 "클라우드 동기화" 버튼** (`pushProjectToCloud`) | 사용자가 누를 때 | 사진 업로드 + `ps_projects` + `ps_facilities`(시설물 통짜 `data` blob) |
| **불러오기** (`pullProjectFromCloud`) | 사용자가 누를 때 | 클라우드 프로젝트를 **새 ID 새 프로젝트로** 복제(덮어쓰지 않음) |
| **머지 풀** (`pullCloudChanges`) | online 복귀 시 | `ps_facilities` 통짜 `data`로 로컬 site 덮어쓴 뒤, `ps_inspection_points`를 마커 ID 기준 재병합 |

- **OCC 충돌**: `detectAndRecordConflict` / `resolveOccConflict` — `revision` 비교. 해결책 3종: `keep_local`(강제푸시) / `accept_cloud`(로컬에 클라우드 덮기) / `save_copy`(로컬을 새 ID 사본으로 보존 후 클라우드 수용). **자동 병합 없음 — 사람이 통짜로 선택.**
- **엔티티 단위 sync 엔진은 구현돼 있으나(`syncSingleEntity`가 project/facility/inspection_point/photo/existing_damage 모두 처리) 앱의 저장 경로에 연결돼 있지 않다.** `queueCloudSync()`가 project 1건만 큐에 넣음.

### A-4. 도면/지도 마킹 렌더링
- `.img-frame` (절대배치, `transform-origin:0 0`) 안에 `<img class="base">` + `.marker` 여러 개.
- 확대/축소: `applyTransform()` → `frame.style.transform = translate(...) scale(zScale)`. `zoomAt`/`updatePinch`가 앵커 고정 스케일.
- **`.marker`는 `.img-frame`의 자식** → `width:20px; left:x%` 로 배치되며 `scale(zScale)`을 그대로 상속받아 **확대 시 핀도 같은 비율로 커짐**.
- 좌표 데이터: `xPct`/`yPct` (프레임 대비 %), `handleTap`에서 역변환으로 계산.

### A-5. 출력 (이미 구현)
- **Word `.docx`** (`btnWord` 클릭 핸들러, 14091~): 제목 → 도면별 전체위치도(마킹된 이미지 `buildMarkedImageFor`) → 지도 위치도(`buildRealMapImage`) → **기존손상 현황표** → **기존 vs 현재 비교표**(existingDamageId 연결분만, `compareMeasurements`) → **지점별 2열 표: 사진 밑에 손상명·구분·구성요소·규모·원인·파괴요인·평가·보수공법·보강공법·긴급도·조사자의견·근거 + 비고**.
- **손상비교 Excel** (`btnExportComparisonExcel`, 10688~): 6시트 — 요약 / 상세비교(증감량·증감률·변화상태) / 신규손상 / 보수·소실·미확인 / 손상규모상세(measurementItems) / 손상이력(activityLog).
- **기존손상 Excel Import/Export** (`EXCEL_COLUMNS`, 10604~): 컬럼 = `ID·손상명·위치·조사년도·구성요소·손상규모·원인·보수방안·상태·비고`. Import는 ID 중복 시 **건너뛰기**(덮어쓰지 않음), 손상명 없는 행 제외, 최대 2000행.
- 모든 출력은 **시설물(site) 1개 단위**. 프로젝트 전체 집계 없음.

## B. 5대 항목 정밀 진단

### 1) CAD 손상현황 → 피치샷 "기존손상" 브릿지
**현황**: 기존손상 Import는 `손상명` 컬럼만 필수. CAD 스킬(외부, 이전 세션의 "슬로프페이스맵")은 `구간 / 위치 / 손상명 / 규모구분·값·단위`를 뽑되 **"부위"가 손상명 안에 괄호로 섞임**(`균열 (1소단측구)`), 규모도 `구분/값/단위`가 분리됨.

**갭**:
- 앱 `ExistingDamage`에 **`구간(section)` 필드 없음**. `부위`는 `component`로 대응 가능.
- 규모: 앱은 자유텍스트 `measurement`(`"길이 2.0m, 폭 0.5mm"`)를 읽음. 스킬 출력의 `구분/값/단위` 3열을 이 문자열로 합쳐줘야 함.
- Import 파서(`excelImportInput` change 핸들러)가 `구간` 컬럼을 안 읽음.

**할 일**:
- (앱) `ExistingDamage`에 `section` 추가 — 폼(`openExistingDamageForm`/`edSave`), `EXCEL_COLUMNS`, Import 파서, `renderExistingDamages` 표시, Word/Excel 출력 컬럼. **기존 필드 불변, 추가만.** 마이그레이션 불필요(없으면 `''`).
- (스킬) 5번째 시트 자동생성: `ID·손상명·위치·구간·조사년도·구성요소·손상규모(합쳐진 문자열)·원인·보수방안·상태·비고` — 앱 `EXCEL_COLUMNS`와 1:1. "부위"를 손상명에서 분리해 `구성요소`로.

### 2) 같은 시설물 → 팀원 조사자료 취합
**현황**: 마커 ID는 랜덤 생성이라 절대 안 겹침. `ps_inspection_points` 테이블 + `syncSingleEntity`(마커 단위 upsert + revision OCC) + `pullCloudChanges`(마커 ID 기준 union 병합) 로직은 **이미 존재**.

**갭 (핵심)**:
1. **저장 경로가 엔티티 sync에 연결 안 됨**. `queueCloudSync()`는 `ps_projects` 1행만 큐잉 → 자동 동기화로는 마커/사진/기존손상이 클라우드에 안 올라감. 실제로는 **수동 버튼(`pushProjectToCloud`)이 시설물 통짜 blob을 덮어쓰는 방식**이 유일한 실동작. 이전 세션 진단("통짜 데이터")이 맞음.
2. `pullCloudChanges` 1단계에서 `sites[idx] = Object.assign({}, sites[idx], rf.data)` → **원격 시설물 blob의 markers 배열이 로컬 markers를 통째로 덮음**. 2단계 inspection_points 병합이 뒤따르지만, **클라우드에 아직 없는 로컬 전용 마커는 1단계에서 소실** 가능(pendingKeys는 `facility:` 키만 보호, 개별 마커 미보호). → 회귀보호 규칙 4번(ZERO DATA LOSS) 위반 소지.
3. 마커/사진/손상 병합이 **whole-object `Object.assign`** — 같은 마커에 A는 사진, B는 손상정보를 각각 추가하면 한쪽 손실. `photos[]`·`damages[]`를 **자식 ID 기준 union**해야 함.
4. `existingDamages`는 시설물 blob 안에만 있음 → 팀원 2명이 같은 시설물 기존손상 편집 시 마지막 facility upsert가 이김(revision OCC가 통짜 충돌로만 잡음).
5. **자동 sync 의심 버그**: `queueCloudSync`가 revision 미지정(항상 1) → `syncSingleEntity('project')`는 `expectedRevision=1`로 검사하는데 최초 동기화 후 클라우드 `data.revision`이 2가 됨 → **이후 모든 자동 sync가 거짓 충돌(conflict) 기록** 가능성. (git log의 "loading freeze" 수정들과 연관 의심 — 검증 필요.)

**할 일 (단계적)**:
- **2-A. 엔티티 sync 배선**: `saveState` 후 변경된 site/marker/existingDamage를 각각 `enqueueEntitySync`. `revision`은 로컬 엔티티의 `.revision`을 넘김. 거짓충돌 버그 수정.
- **2-B. 풀 병합 안전화**: `pullCloudChanges` 1단계에서 `rf.data.markers`를 **직접 덮지 말고**, 시설물 스칼라 필드만 병합 + 마커는 2단계 union에만 맡김. 로컬 전용(미동기) 마커는 pending 큐 유무와 무관하게 보존.
- **2-C. 자식 배열 union**: 마커 병합 시 `photos`는 `photo.id` 기준, `damages`는 `damage.id` 기준 합집합. 같은 자식 ID를 양쪽이 수정한 경우만(진짜 충돌) 사용자 확인.
- **2-D. 기존손상 엔티티화**: `existing_damage`를 `ps_inspection_points`처럼 독립 sync 대상으로. (이미 `syncSingleEntity`에 케이스 있음 — 배선만.)
- **2-E. "취합" UX**: 프로젝트/시설물 화면에 "팀원 조사자료 가져오기" → 자동 union 결과 요약(추가 N지점 / 갱신 M지점 / 확인필요 K건) 표시.

### 3) 시설물별 자료·보고서 출력
**현황**: **요청 구조가 이미 거의 구현됨** (A-5 참조). 손상비교 Excel = 물량표+증감, Word = 위치도→기존손상표→비교표→지점별 사진+손상정보.

**갭**:
- 물량표(기존손상 Excel/Word 표)에 **`구간` 컬럼 없음** (1번과 연동).
- "기존 배치와 동일한 물량표" = CAD 원본 순서/구조 유지가 아직 보장 안 됨(Import가 행 순서는 보존하나 `구간` 그룹핑 표시는 없음).
- 신규손상이 비교표와 **분리 출력**됨 — 요청은 "물량표에 기존+변화+신규를 함께" 정리.
- 변화상태(`changeStatus`) 수기 입력 의존 — `compareMeasurements`는 자유텍스트 첫 숫자만 비교(부정확). `measurementItems` 항목별 비교로 승격 필요.
- 보고서 양식(로고·표 서식·문구)은 **사용자 제공 양식 대기**.

**할 일**:
- 물량표에 `구간` 컬럼/그룹 헤더.
- Word/Excel에 "**손상현황 통합표**" 1개: 행 = 구간·부위·위치·손상명, 열 = 기존규모 / 현재규모 / 증감치수 / 증감률 / 증감여부 / (신규는 기존규모 공란·"신규" 표시).
- 항목별 규모 비교(`measurementItems` type별 매칭 → 각각 증감).
- 양식 받으면: **로직 불변, 출력 서식만 교체**(docx children 구성/스타일 레이어 분리).

### 4) 프로젝트 전체 집계
**현황**: 없음. 모든 출력이 `currentSiteObj()` 단위.

**할 일**:
- `exportProjectReport(projectId)` 신규: `sites.filter(s=>s.projectId===id)` 순회.
- Excel: 시설물별 시트 + "프로젝트 요약" 시트(시설물 수, 총 지점, 기존손상/신규/증가/감소 집계).
- Word: 표지 → 시설물별 섹션 반복(기존 site 단위 로직 재사용) → 프로젝트 총괄표.
- 팀원 몫 포함 = 2번(취합)이 선행돼야 완전.

### 5) AI 최종보고서 파이프라인 (← "사무실모드" 대체)
**사용자 결론에 동의**: 별도 사무실모드 데이터는 불필요. 이미 `appWorkMode`는 순수 화면 선호값이고 "현장에서도 사무실 업무 전부 가능"하게 설계돼 있음(코드 주석 4725~). 취합 → 구조화 산출물(JSON/Excel) → AI 에이전트가 최종 보고서 생성이 더 효율적.

**설계**:
- **경계 고정**: 앱은 "검증된 구조화 데이터"까지만 책임. 산출물 = ① 프로젝트 집계 Excel ② 정규화 JSON 번들(project+sites+markers+damages+existingDamages+비교결과+마킹위치도 PNG·지점사진, 상대경로).
- **AI 단계 (앱 밖, 스킬/에이전트)**: JSON 번들 입력 → 기관 보고서 양식(.docx 템플릿)에 매핑 → 손상 서술문 자동작성(규모/원인/보수방안 문장화) → 총평·등급 초안 → 검토용 `.docx` 출력.
- **재현성**: 번들에 `schemaVersion`·생성시각·소스 revision 포함. AI 출력은 항상 "초안", 사람이 최종 승인.
- 스킬 이름(안): `peachshot-report` — 입력 JSON 번들, 출력 채워진 docx + 변경 로그.

## C. 도면 마킹 겹침 — 원인 확정 & 처방

**원인**: `.marker`가 `scale(zScale)` 되는 `.img-frame`의 자식이라 확대 시 핀 크기와 핀 간격이 **같은 비율로** 커진다 → 아무리 확대해도 겹침이 안 풀림(지도앱과 정반대).

**처방 (우선순위순)**:
1. **핀 화면고정 크기** (권장, 근본원인): `renderMarkers`에서 각 `.marker`에 `transform: translate(-50%,-50%) scale(1/zScale)` 역보정, `applyTransform` 때 갱신. `::after` 꼬리·`margin -10px` 중심보정도 함께 정리. → 확대할수록 핀 대비 간격이 벌어져 겹침이 자연 해소. **데이터(xPct/yPct) 불변, CSS/JS 소규모.**
2. 기본 핀 20→18px 미세 축소(선택).
3. 극단적 밀집: 탭 지점 반경 내 핀 2개 이상이면 "이 근처: 12·13·14" 미니 선택목록(`handleTap` 보완, 선택).

**회귀 위험**: `renderMarkers`는 보호목록 아님. `handleTap` 좌표 역변환은 `zTx/zScale` 기반이라 핀 시각크기와 무관 → 탭 정확도 영향 없음. `.marker.selected`의 `transform: scale(1.25)`와 충돌하므로 selected도 `scale(1.25/zScale)`로 통합 필요.
