# CHANGE IMPACT REPORT — 지점 삭제가 클라우드에 반영되도록 수정 + 갑작스런 종료 기록 (v112)

## 1. 문제
웹앱에서 지점을 삭제하면(`deleteMarker`) 지점이 기기 안의 휴지통으로만 가고 **클라우드(`ps_inspection_points`)에는 삭제가 올라가지 않는다.**
- 원인: 지점을 클라우드 큐에 넣는 `queueEntitySyncForFacility` 는 지금 `site.markers` 에 있는 지점만 큐에 넣는다. 삭제된 지점은 `site.markers` 에서 빠지므로 삭제 작업(`operation:'delete'`)을 큐에 넣는 코드가 어디에도 없다 (`syncSingleEntity` 는 삭제를 처리할 수 있게 이미 짜여 있으나 호출되지 않는다).
- 결과: 데스크(피치샷 데스크)와 팀원이 삭제한 지점을 계속 받는다 (2026-10-26 지점 9·22·25·37·51).
- 같은 뿌리의 또 다른 문제: pull(팀원 최신자료 가져오기·프로젝트 불러오기)은 클라우드에 있는 지점이 로컬 `markers` 에 없으면 "항상 받는다"고 되어 있어, 삭제한 지점이 휴지통에서 되살아날 수 있다. 삭제가 클라우드에 올라가면 pull 이 `deleted_at` 이 있는 행을 무시해야 한다.

## 2. 변경 내용 (최소 패치)
| 위치 | 변경 |
|---|---|
| `deleteMarker` 직후 / Ctrl+Z "찍기 취소" 직후 | `queueMarkerDeleteSync(m)` 호출 1줄씩 추가 (둘 다 `try` 로 감싸 실패해도 삭제 흐름에 영향 없음) |
| 새 함수 `queueMarkerDeleteSync`, `findTrashedMarker` (`deleteMarker` 바로 앞) | 삭제 작업을 큐에 넣는다. 내가 만든 지점만(팀원 지점은 기존 규칙대로 안 올림). 같은 지점의 "마지막으로 큐에 넣은 내용" 서명을 지워, 복원했을 때 다시 올라가게 한다 |
| `syncSingleEntity` 의 `inspection_point` 분기 | ① 삭제 작업이면 휴지통에 있는 지점 내용을 그대로 실어 보낸다(빈 내용으로 덮어쓰지 않도록). 휴지통에서도 못 찾으면 행 내용은 건드리지 않고 `deleted_at` 만 기록한다. ② 클라우드 행을 읽을 때 `deleted_at` 도 읽고, 삭제 표시가 있는 행은 "내용이 같으니 올릴 것 없음"으로 건너뛰지 않는다(= 복원하면 `deleted_at` 이 지워진다) |
| pull 3곳 (`ps_inspection_points` 조회) | `.is('deleted_at', null)` 한 줄씩 추가 — 삭제 표시된 지점은 받지 않는다 |
| `PS_BUILD` / `service-worker.js` CACHE_NAME | v111 → v112 |

## 3. 건드리지 않는 것
- `idbDeleteInspectionPoint` 포함 IndexedDB 함수, `saveState`/`performSaveState`/`loadState`, `queueCloudSync`, `pushProjectToCloud` 본문.
- 삭제·복원 화면(휴지통 UI), 사진 삭제, 시설물 삭제, 도면.
- `syncSingleEntity` 는 보호 대상 함수지만 이 수정과 직접 관련된 `inspection_point` 분기(삭제 처리·`deleted_at`)만 고친다. 다른 분기(project/facility/damage/existing_damage)는 그대로.
- `pullEntityChanges` 는 조회 3곳에 필터 한 줄씩만 추가한다 (병합 로직은 그대로).

## 4. 영향 분석
| 항목 | 영향 | 판단 |
|---|---|---|
| 오프라인 삭제 | 삭제 작업이 큐에 쌓였다가 온라인 때 올라간다. 지점 자체는 휴지통에 그대로 있어 데이터 손실 없음 | 안전 |
| 삭제 후 복원 | 큐 서명을 지웠으므로 복원한 지점이 다시 올라가고, 클라우드 행의 `deleted_at` 이 지워진다 | 시험함 |
| 삭제 후 pull | 삭제된 행은 받지 않으므로 휴지통 지점이 되살아나지 않는다 (기존에는 되살아날 수 있었음) | 개선 |
| 팀원이 만든 지점 삭제 | 내가 올리지 않는 규칙 유지(큐에 안 넣음). 이 기기에서만 휴지통으로 감 | 기존 동작 유지 |
| 휴지통 "완전삭제" | 이미 삭제 표시가 올라가 있어 추가 동작 없음 | 영향 없음 |
| 클라우드 데이터 | 행은 지우지 않고 `deleted_at` 만 기록(소프트 삭제). 복원 가능 | ZERO DATA LOSS 유지 |
| 데스크 | 이미 `deleted_at` 행을 받지 않도록 되어 있어 코드 변경 없음 | 영향 없음 |
| 다른 팀원 기기 | 이미 받아 둔 삭제 지점은 그 기기에 그대로 남는다(자동 제거는 이번 범위 밖) | 한계로 명시 |
| 이미 삭제했지만 클라우드에 남아 있는 지점(예: 지점 9·22·25·37·51) | **자동으로는 정리되지 않는다.** 휴지통에서 "복원 → 다시 삭제"하면 이번 수정으로 클라우드에 반영된다 | 안내 필요 |

## 10. v117: 사진을 화면에 필요할 때만 메모리에 올린다 (시설물을 열 때 사진 전체를 올리던 방식 변경)
- **문제**: 시설물을 열면 그 시설물의 사진 원본(base64, 장당 약 2MB)을 전부 메모리에 올려 두었다(`loadSite`). 사진이 100장이면 약 200MB, 수백 장이면 600MB 이상이 되어 아이폰이 앱을 강제 종료했다. 9월·10월에 여러 번 부분적으로 줄였으나 이 부분은 남아 있었다.
- **변경 요약**: `loadSite` 에서 사진 전체를 올리는 줄을 없애고(기기 저장소 `photoBlobs` 의 원본은 그대로), 사진이 필요한 곳에서 그때그때 읽는다.
  - 새 도우미(`hydratePhotoBlobs` 앞): `setImgFromStore`(저장소 파일을 blob 주소로 바로 연결 — data URL 을 만들지 않음, 예전 kv 방식 사진은 읽으며 옮김), `lazyThumb`(기록목록 썸네일을 3개씩 차례로), `ensurePhotoSrc`, `photoBlobForExport`, `hydrateMarkerTemporarily`(지점 하나씩 올렸다가 내려놓음).
  - 적용 위치: ① 기록목록 썸네일(카드·표, 넓은 화면) ② 지점 상세 사진 선택 줄 썸네일 ③ 촬영창 사진 줄과 크게 보기 ④ 사진 다운로드 버튼 ⑤ 사진 주석 열기 ⑥ ZIP 내보내기(저장소의 파일을 그대로 담음) ⑦ Word 내보내기(지점마다 올렸다 내림) ⑧ 팀원 최신자료 가져온 뒤 사진 받기(저장소에 없는 사진만, 한 지점씩 받고 내려놓음).
  - 이미 필요할 때 불러오던 곳(지점 상세 창·백업·보고서·클라우드 업로드)은 그대로.
- **점검 중 정정**: "기록목록에는 사진이 안 나온다"는 것은 휴대폰의 한 줄 목록만 맞고, 넓은 화면(PC·태블릿)의 기록목록과 표에는 지점마다 첫 사진 썸네일이 나온다. 이 화면도 위 ①로 처리했다.
- **보호 함수**: `loadSite` 1곳만 변경(사진 전체 불러오던 줄 삭제). `saveState`·`performSaveState`·`addPhoto`·`hydratePhotoBlobs`·IndexedDB 함수·`syncSingleEntity` 등은 v116 과 본문이 동일(시험으로 비교).
- **안전 원칙**: 메모리에서 비우는 것은 이번에 도우미가 직접 올린 사진 중 저장소에서 읽은 것이 확인된(`blobExtracted`) 것뿐이고, 지금 열어 본 지점·방금 찍은 사진·이미 메모리에 있던 사진은 건드리지 않는다. 기기 저장소·클라우드의 사진은 어떤 경우에도 지우지 않는다. 저장소에서 못 읽으면 비우지도 지우지도 않는다.
- **보이는지 판단하는 방식(IntersectionObserver)은 쓰지 않는다**: 실브라우저 시험에서 이 창에서는 동작하지 않아(썸네일이 안 뜸) 순서대로 읽는 방식으로 바꿨다.
- 시험: `scratch/test_lazy_photos.js`(도우미 30건), 실브라우저(아래).
  - 사진 11장이 저장소에 있는 상태로 다시 열면 앱 시작 직후 메모리 사진 0장(예전: 전부).
  - 넓은 화면 기록목록 썸네일 4/4 표시(blob), 크게 보기·ZIP(사진 8장 전부 포함)·Word(사진 8장 + 도면 이미지, 지점 제목 4개) 정상, 팀원 지점(사진은 클라우드에만 있음) 가져오기 후 사진 2장 받아 저장소에 저장·썸네일 표시, 두 번째 가져오기는 다시 받지 않음.

## v120 — 손상명 라이브러리 + 부위 묶기 + 상태양호
- **요청**: 손상마스터 관리가 불편 → 손상명을 구분 없이 한곳에 모으고 규모(폭·길이·너비·개소 등, 복수 선택)를 같이 세팅, 부위별로 손상명을 가져와 묶기. 규모가 형식마다 다른 손상명은 합집합(유실 = 너비+길이+깊이+개소)으로. 부위만 고르고 손상명이 없으면 상태양호로 본다.
- **분석(기준DB)**: 손상명×부위×형식 131건 = 서로 다른 손상명 61개, 규모가 다른 손상명은 유실·누수 2개뿐, 규모 설정이 없는 손상명 8개. "수량"과 "개소"는 같은 뜻 → "개소(EA)" 통일.
- **변경(index.html)**:
  1. **읽는 지점 하나**: `getMeasurementFields` 가 `dmLibraryEffective()`(기준DB·공용/프로젝트/조직 마스터의 같은 이름 규모를 합집합 + 사용자가 라이브러리에서 바꾼 `damageLibrary`)를 먼저 본다. 기존 마스터 저장 구조(시설물종류×형식×부위 배열)·저장 3종(프로젝트/조직/이 기기)은 변경 없음.
  2. 이 기기 저장소 키 `point-shot-damage-library`(손상명 → 규모 항목, 직접 등록 여부). 팀 공유는 아님.
  3. 손상마스터 화면: [📚 손상명 라이브러리](검색·규모 칩 복수 선택·직접 항목·새 손상명 등록·기본값으로/삭제), 부위 카드 [📚 손상명 가져오기](체크로 묶기/빼기, 새로 담는 손상명은 규모와 기존 원인·보수 문구를 함께 가져옴, 모두 빼도 부위는 유지), 손상명 카드의 규모는 라이브러리 값 표시 + [규모 변경].
  4. 현장 입력: 규모 항목이 3개 이상이면 3번째부터 값이 빈 칸은 접고 "＋ 규모 항목 더 보기". 부위만 고르고 손상명이 없으면 규모칸 대신 "✓ 상태양호" 안내, 목록·복사·Word 에 "상태양호 (부위)"로 표시.
  5. 예전 "수량" 값은 "개소"로 옮김(값 보존, `dmNormalizeMeasurementItems`).
- **영향 범위 / 위험**: ① 이미 진행 중인 프로젝트의 규모 입력 칸이 합집합으로 늘 수 있음(누수·유실만 기본값이 바뀜, 값 저장 형식 동일). ② 라이브러리에서 규모 항목을 빼면 그 항목의 기존 입력값은 다음 편집 때 규모 문자열에서 빠짐(데이터는 지우지 않음 — 항목을 다시 켜면 보임). ③ 라이브러리는 이 기기 전용이라 기기마다 다를 수 있음. ④ 데스크는 변경 없음(규모 문자열 형식 동일; 데스크의 "(손상명 없음)" 표시는 이번에 안 바꿈).
- **시험**: `scratch/test_damage_library.js`(23건: 61개 정리·유실/누수 합집합·수량→개소·사용자 변경·직접 등록·상태양호 표시 등, 실제 STANDARD_DB 로 실행), 실브라우저(가짜 Supabase)에서 라이브러리 화면·칩 수정·새 손상명 등록·부위 가져오기·규모 변경 이동·상태양호 안내·더 보기 확인, 웹앱 시험 16개 전부 통과. 미확인: 실제 폰 화면 배치, 조직(팀) 공유 마스터와의 상호작용.
